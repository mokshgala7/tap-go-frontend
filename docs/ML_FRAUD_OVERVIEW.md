# Fraud detection in Tap&Go: an overview for an examiner

This page explains, in plain language, what the machine-learning part does, how good it is (and is not), and how the backend uses it.
All performance numbers are **synthetic/demo-derived, not real-world performance**: the project has no labelled real fraud, so the model
was trained and tested on generated data. The details and code are in `ml/`.

## 1. What V6 is

* **XGBoost** classifier (gradient-boosted trees) with monotone constraints, so that a higher fare or a thinner history can never make a payment look *safer*.
* **39 features**, all computed from the passenger's own earlier completed rides plus the current ride: how far the fare is from the passenger's usual fare, time of day (day/night, IST),
  how many rides the passenger has, how recently and how often they ride, whether the driver is familiar, vehicle type, weekend. No location (GPS) is used.
  The list is in `ml/reports/evaluation_summary.md` and `ml/v6/features/FEATURE_DICTIONARY.md`.
* **Output:** a risk score and a flag. The **decision threshold is 0.0633**; a score at or above it is "flagged". **The score is uncalibrated**: it ranks payments by risk, it is not a probability of fraud,
  and 0.0633 does not mean "6% chance".
* **The model only scores.** It never approves, rejects, charges or sends anything. The backend decides what to do with the flag.

## 2. How it was trained and evaluated

* **Data:** generated by `ml/v6/data/generator_v6.py` (fixed seeds): about 234,000 development rides from about 3,000 fictional passengers and 750 fictional drivers, with 17 scenarios (ordinary trips, airport
  and long trips, retries, card testing, overcharging drivers, compromised accounts, ...). About 1.3% of rows are fraud. The full data is not stored in git; a 1,000-row sample is (`ml/data/`).
* **Process:** 10 candidate models were trained; each had to pass ten written requirement tests ("gates", for example *a familiar driver cannot hide an unusual fare*, *no GPS*, *the 10-minute boundary is exact*)
  before accuracy was even considered. One candidate passed, was **frozen**, and only then was a fresh test world (T3, 238,790 rides) generated and scored. The threshold was fixed on validation data (highest recall with a
  false-positive rate of at most 2%).
* **Result on the fresh test world (synthetic):** precision 22.55%, recall 49.11%, F1 0.309, PR-AUC 0.440, false-positive rate 2.17%. About 2.8% of all rides are flagged, and **4.32% of legitimate night rides**
  (1.70% by day) would be asked for an OTP. Full tables, intervals, the V4/V5 comparison and charts: `ml/reports/evaluation_summary.md`.

**Which test set the figures come from** (all synthetic/demo-derived, not real-world performance):

| Set | Role | Rides | Chosen on it, or sealed? | Precision | Recall | False-positive rate | Night legitimate OTP rate |
|---|---|---|---|---|---|---|---|
| D6 validation | selection data | 58,512 | used to choose the model and the threshold | 21.96% | 42.82% | 2.00% | not reported |
| T3 `D6_fresh` (final test) | held-out, sealed until V6 was frozen | 238,790 | sealed | 22.55% | 49.11% | 2.17% | 4.32% |
| `F_fresh` T3 (extra deployment check) | a different synthetic world made for an earlier experiment | 231,940 | not used to choose V6 | 21.22% | 48.88% | 2.51% | not found in the files |

The figures quoted in the previous paragraph are the T3 `D6_fresh` row. The two large sets are different generated worlds, so do not mix their numbers; see `ml/reports/evaluation_summary.md` for sources.

## 3. How the backend uses it

Every ride payment (NFC tap, QR, wallet pay) goes through one gate, `backend/app/services/fraud_gate.py`. There are two groups of passengers.

**Personal-model users (the ids in `TAPGO_FRAUD_ENFORCE_USER_IDS`).** The gate runs the V6 model and a plain **10-minute rule** (a payment within 600 seconds of the previous completed ride). If either fires, the payment
is **not** made: the passenger gets a 6-digit code by email and the code must be entered on the **driver's POS**. The model uses the passenger's own history ("personal profile"); that profile only becomes fully personal at
**100 completed rides**, and below that it is blended with population averages.

**Everyone else follows the fixed new-account policy.** A payment of **Rs 300 or less is allowed** on its own; a payment **above Rs 300 cannot go through on its own and needs the emailed OTP, entered on the POS**.
The usual checks still come first (for example an insufficient wallet balance is refused before any code is sent), and the **10-minute rule does not apply** to this group.
**This policy is plain backend code with a fixed amount threshold. It is not the model**: the V6 score is still computed and stored for these users, but it does not decide anything and a scoring failure never blocks them.
It is switched on with `TAPGO_NEWUSER_POLICY=enforce` (default `off`, nothing changes until it is set) and the threshold is `TAPGO_NEWUSER_OTP_ABOVE` (default 300, exclusive: 300 passes, 301 asks for a code).
*Status note: the new-account policy and the POS-only code entry are implemented on the branch `pos-otp-newuser-ui`; this page describes them as designed.*

**For both groups:**
* **No money moves without a verified OTP.** The code is single-use, valid for 5 minutes, allows 3 wrong attempts, is stored only as an HMAC hash, and is bound to the passenger, driver, amount, channel and payment key.
* A **wrong code (attempts used up), an expired code or a cancel fails the payment**, records it as failed, moves nothing and **emails the passenger a failure notice** (one email per failed payment).
* If the code cannot be emailed, an enforced payment is declined, never let through.
* Every decision is recorded (`fraud_assessments`) without names or contact data. `backend/docs/FRAUD_V6_DEPLOY.md` has the environment variables, deploy order and rollback.

## 4. Limitations (please read)

* **Synthetic data only.** The model has never seen a real fraud case. The numbers above describe the generator's world; real performance is unknown until shadow-mode data with confirmed outcomes exists.
* **Demo accounts.** The live demonstrations use a few demo passengers with seeded ride histories; the personal profile for a passenger is meaningful only from **100 completed rides**.
* The score is **uncalibrated** and V6 scores a **lower PR-AUC than V4/V5** on the synthetic data: it chooses to challenge genuinely expensive trips (about one in four of them in the test world) rather than let a familiar driver hide an unusual fare.
  Some fraud kinds are largely missed (for example a familiar driver overcharging).
* **SMS OTP is not implemented** (it needs telecom DLT registration). Codes go by email only; a passenger with no email on file is declined when a code is required.
* The new-account rule is a blunt, fixed-amount policy, not learning.
* Not verified in production and not tested on real hardware at scale.
